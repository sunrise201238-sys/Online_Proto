把離線指揮模式（全 BOT 駕駛＋下令玩法）搬進伺服器權威的線上對戰：五層程式碼逐行審計後的可行性、工程分解、風險與待拍板決策。

可行，且比初評樂觀線上 BOT（shared ai.js）已具備離線 BOT 的全部反射等價物；尋路、Boost 經濟、動量、計時模型與離線同構。指令層是「掛覆蓋」不是「重寫腦」。
真正的主工程換了位置不是移植 BOT，而是「資訊隱藏管線」：現行快照把整個賽局狀態原樣廣播給全房——敵方 Boost、彈藥、冷卻、鎖定目標現在就全裸。任何指令欄位上車前，過濾層必須先落地。
你的兩條規則都成立排隊房各選＋入場鎖死：小工程，且反而省掉線上換手交接。藏敵方 Boost：屬於過濾層工作的一部分，順帶把指令狀態、鎖定推斷一起藏。

01審計方法與關鍵事實

五個並行代理各讀一層（線上 BOT／模擬管線／狀態與導航／伺服器／client 線上層），所有結論附行號證據，重點交叉驗證過。以下是承重的事實。

好消息：指令層的每個構件在 shared 裡都有現成模板

  • 線上 BOT 反射面幾乎完備。防禦態（垂直脫離＋400ms 再垂直化）、反光閃避（隨機 400/800/900ms 反應 → i-frame 墊步 → 520ms 防禦衝刺）、換彈搶掩體（A* 尋路＋held 擺動）、墊步、硬直、Engage 環繞（切線＋距離拉力）全部存在。狀態機優先序 Defense > Maze > Engage > Pursue。ai.js:493-582 · 698-860 · 1149-1231 · 1492-1513 · 1590-1707
  • 衝刺算式與離線完全同式：vel = dir × sprintSpeed(11.76) ＋ inheritMomentum(×1.5)，衝刺極速是動量堆出來的（裸 sprint 比走路 16 還慢）——指令衝刺必須重用 startDash／動量管線，不能手搓速度。ai.js:1738-1742 · tick.js:296-304 · actions.js:288-292
  • Boost 經濟同構：dash 扣 1.1/tick、回充 4.59/tick、500ms 回充暫停、cap 250、empty-recover——2.1b 的「滿格閂鎖＋50 底線」是純新增的小狀態機；BOT 自己的 Pursue 甚至已有「滿格才衝」的遲滯閂（BOT_BOOST_RESERVE=250）可直接仿。movement.js:24-54 · ai.js:1281-1283
  • 尋路與驗單工具全在伺服器端：navGridFor(arena) 每張圖每進程只建一次（WeakMap 快取）、findPathOnGrid／smoothPath 已匯出、導航格自 2026-08-14 起多層（每格至多 4 個站立高度）涵蓋多樓層地圖。離線的「終點 6u 內＋樓層可站」驗單只是薄包裝。ai.js:104-113 · navgrid.js:8-26 · 558 · shared index.js:49
  • 計時模型零阻力：整個 sim 使用絕對毫秒 xxxUntil 慣例對比 server clock——20 秒錨定就是 anchorUntil = now + 20000，一行入慣例。tick.js:271-281
  • Client 渲染層幾乎免改：快照鏡射（mirrorFighterToMech）把 hp／boost／位置寫進與離線相同的 mech 欄位，縮景 HUD 讀的每個欄位線上都有；標記層以 slot 為鍵、不綁 mech 物件，Trio 換機可存活。main.js:7472-7504 · 11144-11216

壞消息：現行協定是「全裸廣播」

  • 快照零過濾：buildSnapshot 原樣送出 state.fighters（引用直傳），一份相同快照 io.to(lobby.id) 廣播全房——敵方 Boost、彈藥、全部冷卻、狙擊充能、targetId（鎖定目標）、甚至 BOT 的 ~40 個 botXxx 意圖欄位，今天就全部送到對手手上。藏 Boost 是新能力，不是回歸修復。state.js:338-352 · server index.js:256-266 · 341
  • 指令欄位上車即洩漏：把 cmdMove／cmdLock 照離線習慣放上 fighter，下一個 tick 敵人就看得到你的目的地與鎖定。程式庫已有警語與先例：BOT 路徑刻意存 matchState._navPaths 而非 fighter，就是為了避開序列化。ai.js:926-928 · 987-997
  • targetId 是既存的鎖定洩漏：force lock 寫的就是 targetId，光藏 cmd 欄位、不處理 targetId，等於沒藏。過濾時要一併裁決哪些敵方欄位是「本來就看得見的表演」（紅鎖、玻光、步進）哪些是私密。state.js:160-166 · 193-194

03風險登記簿

  • 過濾層必須第一個落地任何 cmd 欄位在過濾層之前上 fighter 都是即時洩漏；過濾採 allowlist 才不會被未來新欄位默默突破。teammates 應互見 → per-team 兩份變體即可（不必 per-socket 四份）。
  • botSlots 是四用途集合，不能直接塞指揮人類它同時代表「用 tickBot 驅動」「忽略此 socket 輸入」「玻光反作弊的非人類判定」「廣播給 client 的資訊」。指揮人類需要獨立的 commandSlots，否則玻光反作弊對他們失效、訂單訊息被當輸入丟棄。server:277 · 309-310 · 407
  • BOT 狀態機會搶指令「背向敵人行軍」超過 2 秒觸發 noLoSTime 劫持進 Maze；無存活目標時 tickBot 直接 early-return，指令單位會凍住——驅動要掛在該檢查之前並 pin 住偵測時鐘。ai.js:459-460 · 663-688 · 1033-1051
  • action 欄位不可承載指令狀態tickBoost 每 tick 覆寫 fighter.action，且過熱／耗盡時強制改寫——指令狀態機必須自持欄位，並把正確的 action 字串交給 tickBoost（'dash' 才扣氣）。movement.js:35-36
  • botControlled 的副作用跳躍冷卻 1.5s 下限、飛行單位地面化——離線指揮模式本來就是 BOT 駕駛，行為其實一致，但值得知情。actions.js:278-283
  • 時鐘域陷阱離線指令計時用 performance.now()；線上鏡射欄位是 server clock（hudNow）——client 端任何比對必須換時鐘，否則圖示與圈圈時序漂移。main.js:8707-8713
  • 裁剪欄位要「歸零」不要「刪除」client 鏡射無條件寫入（s.boost = fighter.boost），undefined 會讓 HUD 條寬變 NaN；被遮蔽欄位以常數歸零＋client 容錯最穩。main.js:7486
  • 1v1 斷線語意現制斷線即判負；指揮玩家的單位本來就是 BOT、斷了照打——要不要寬限期？做寬限就得建重連身份層（現在完全沒有）。
  • 混搭平衡是未知數BOT 反射超人、戰略笨；「選指揮拿完美閃避」或「指揮＝送頭」的 meta 只能內測裁決。

04待你拍板的設計決策

  1. 2v2 隊友是 BOT 填位時，指揮玩家可否指揮它？建議：可——這是指揮模式最有價值的場景，離線已有雙單位指揮的完整語意。
  2. 人類隊友能否看見你的指令（目的地圈、鎖定）？建議：可見（per-team 過濾）——協同作戰需要，且過濾只需兩份變體。
  3. 對手「選了指揮模式」這件事本身要不要藏？建議：不藏——排隊房自然可見，入場後也無法改。
  4. 1v1 指揮玩家斷線：立即判負（現制）還是 BOT 續打＋寬限？建議：先維持現制，避免第一版就建重連身份層。
  5. 觀戰者看到哪個視角的過濾快照？建議：第一版全視角（私人房觀戰），公開化再收緊。
  6. Trio × 指揮線上第一版要不要一起上？建議：先 Duel——respawn 換機與指令簿記的互動留到第二版。
  7. 敵方 Boost 之外，可推斷氣量的欄位（overheat、sprint-lock）要不要一起藏？建議：一起藏，但保留有視覺表演的欄位（推進器噴焰本來就看得見）。

05建議實作切法

PHASE 0快照過濾層（必須最先）中

buildSnapshot(state, viewerTeam) allowlist 版＋逐 socket 發送＋client 鏡射容錯。順帶收掉現存的 Boost／冷卻／botXxx 洩漏——這一步即使不做指揮模式也值得。

PHASE 1shared 指令層中-大

指令狀態 side-table（仿 _navPaths）→ force lock guard → 移動指令驅動（反射讓行＋狀態機 clock-pinning）→ 衝刺閂鎖 → 錨定環繞 → 伺服器驗單＋開局預熱導航格。每一塊都有行號級的模板可仿。

PHASE 2伺服器房間層小

commandSlots（獨立於 botSlots）、lobby.config.viewMode（跟上 slot swap／host promotion／rematch 三條搬移路徑）、訂單訊息＋rate limit＋ack。

PHASE 3client 接線中

排隊房 chip（記得 staleness 簽名）、dioramaActive per-mode 化、指揮玩家改純內插、等待房預建導航格、指令回聲餵 HUD 圖示、時鐘域統一。

PHASE 4平衡內測—

混搭對局的 meta 觀察：指揮 vs 經典的勝率、反射強度是否需要指揮側專屬調參。

粗略量級（誠實標註為粗估）：以我們平常一輪實作的粒度，全程約 5–8 輪＋內測調整。Phase 0 與 Phase 1 可並行開工（過濾層不依賴指令層）。

審計方法：5 個並行代理逐層閱讀（shared ai / tick·movement·actions / state·navgrid·arena / server / client online），共 58 次工具呼叫；全部結論附 file:line 證據，關鍵斷言（衝刺算式、快照內容、反射旗標）經人工抽驗。
